## 1. Machine overview

**CPU:** 8502, an NMOS 6502 derivative. **The stable illegal opcodes behave as on the 6510** (M).

**Speed:**
- 1 MHz or **2 MHz** via `$d030` bit 0 (H).
- At 2 MHz the VIC-II cannot fetch, so the 40-column screen shows garbage. The **80-column VDC is unaffected**.
- **Rule for the VDC flavor:** blank the VIC-II (`$d011` bit 4 = 0) and run at 2 MHz all the time.
- CIA timers still count at 1 MHz (VICE ✓: the test timed 2 MHz loops in µs).

**C64 mode** (the existing C64 build runs there):
- `$d030` still exists: VICE ✓ reads `$fc`, then `$fd` after writing bit 0; a real C64 reads `$ff`.
- So the C64 engine can detect a C128 and use 2 MHz **in the border lines only**, where the VIC-II isn't fetching (§6).
- The REU works at 1 MHz only; the C128 KERNAL drops to 1 MHz for DMA (M).

## 2. VDC 8563 / 8568

**Access:**
- Only through two ports: `$d600` (write: register number; read: status, **bit 7 = ready**, bit 6 = light pen, bit 5 = vertical blank) and `$d601` (data).
- Every access means writing the register number, polling `$d600` until bit 7 = 1, then reading or writing `$d601`. H

**Memory:**
- 16 KB (early C128s, 4416 DRAMs) or **64 KB** (C128DCR and upgraded machines, 4464 DRAMs).
- Register 28 bit 4 selects the DRAM type (1 = 64 KB layout). H
- **64 KB detection** (VICE ✓: 1 under `-VDC64KB`, 0 under `-VDC16KB`): set R28 bit 4, write `$00` at `$0000` and `$55` at `$8000`, then read `$0000` back. A 16 KB VDC aliases them.

**Key registers** (H, PRG):

| Reg | Use |
|---|---|
| R0–R7 | Horizontal/vertical total, displayed, sync. R6 = rows displayed, R4/R5 = vertical total/adjust |
| R9 | Scan lines per character row − 1 (normally 7). **Lower it for finer attribute cells** (§3) |
| R12/R13 | Display start address (hi/lo). **Page flip = rewrite these two in vertical blank** |
| R14/R15 | Cursor address |
| R18/R19 | Update address (hi/lo) for CPU access through R31 |
| R20/R21 | Attribute start address |
| R22 | Character horizontal size / displayed width |
| R23 | Character vertical displayed size |
| R24 | Bit 7: **0 = block fill, 1 = block copy**. Bit 6 reverse screen, bit 5 blink rate, bits 0–4 **vertical smooth scroll** |
| R25 | Bit 7 **bitmap mode**, 6 **attributes enable**, 5 semigraphics, 4 double-width pixels, bits 0–3 **horizontal smooth scroll** |
| R26 | Foreground/background colour (used when attributes are off) |
| R27 | Address increment per row (row stride beyond the displayed width): **virtual screens wider than the display** |
| R28 | Bits 7–5 character set address, bit 4 DRAM type |
| R30 | Word count: **writing it starts a fill or copy of N bytes** (1–255; 0 = 256) |
| R31 | Data. Read/write at the update address, then the address increments |
| R32/R33 | Block copy source address |
| R34/R35 | Display enable begin/end (horizontal) |
| R36 | DRAM refresh cycles per line |

**Modes:**
- **Text:** 80×25, 8×8 (or up to 8×32) characters from VDC RAM, attributes per cell: 16 RGBI colours, blink, underline, reverse, alternate character set.
- **Bitmap:** 640×200, 1 bit per pixel = 16,000 bytes. With **attributes** each 8×(R9+1) cell gets its own foreground/background colour, which is +2,000 bytes for 8×8 cells.
- **Interlace** (R8): 640×480-ish. Needs 64 KB.
- Other resolutions by reprogramming the CRTC registers: e.g. 640×240 PAL, or 720 wide with overscan. M

**Block copy and fill (the "blitter"):**
- **Fill:** write one byte through R31, set R24 bit 7 = 0, then write the count to R30. The VDC repeats the last written byte over N more bytes.
- **Copy:** set R24 bit 7 = 1, the source in R32/R33, the destination in R18/R19, then write the count to R30.
- Both run inside the VDC while the CPU only polls ready. Maximum 255 (or 256) bytes per operation; chain them for more.
- Only linear runs: a rectangle means one operation per raster row.
- **No masking or logical operations:** transparency needs a CPU read-modify-write.

**Measured in VICE ✓** (PAL x128, 1000 bytes, µs, overhead subtracted):

| Operation | Time | Per byte |
|---|---|---|
| CPU write through R31, polling ready every byte, 1 MHz | 31,211 µs | **31.2 µs** |
| Same at 2 MHz | 21,982 µs | **22.0 µs** |
| CPU read through R31, 1 MHz | 31,150 µs | 31.2 µs |
| Block fill (4 × 250) | 850 µs | **0.85 µs** |
| Block copy (4 × 250) | 1,466 µs | **1.47 µs** |
| Block fill with the CPU at 2 MHz | 748 µs | 0.75 µs |

🔧 There is **no published real-hardware figure** for CPU access speed through R31. A Hacker News post estimates ~28 cycles per byte at 2 MHz (~14 µs); others report faster access in vertical blank. **Treat the VICE CPU-access numbers as a model.** The copy/fill to CPU-write *ratio* (20–35×) is the design signal.

**Design consequences for ISO64-C128:**
- Keep **tile graphics in VDC RAM** (64 KB: 16 KB bitmap + 2 KB attributes × 2 buffers = 36 KB, leaving ~28 KB for tiles). **Draw opaque cells with block copies**, one operation per pixel row of the cell.
- Masked (transparent) cells need CPU read-modify-write at ~20–30 µs per byte. Minimise them:
  1. compose in C128 RAM at 2 MHz, then copy finished bytes to the VDC;
  2. or treat a whole column as opaque wherever the art allows.
- **Scrolling:** R12/R13 (display start) plus R27 (row stride) give **hardware scrolling across a wider virtual bitmap**. The display can pan over a bitmap wider than 80 bytes with no copying: R24/R25 handle smooth scroll within a cell, and the start address handles whole cells. Only the newly exposed strip needs drawing. This is the C128's answer to the REU walk (M; register semantics H).
- **Double buffering:** two bitmaps in 64 KB, flipped by R12/R13 (and R20/R21 for attributes). Do it during vertical blank (`$d600` bit 5) to avoid tearing. H
- **Colour:**
  - 2 colours (RGBI) per attribute cell. ISO64's 4-colour multicolour tiles don't map 1:1.
  - With **R9 = 3 (8×4 attribute cells) or R9 = 1 (8×2)**, attributes become 2× or 4× denser (4,000 or 8,000 bytes). That gives much better colour fidelity at the cost of RAM and draw time.
  - The editor's `c128.js` preview must model whichever choice is made.
- **REU → VDC:** an REU fetch with the C64 address fixed at `$d601` would stream bytes at 1 per µs, faster than the VDC accepts (no ready handshake), so bytes are likely to be lost. L 🔧 Don't plan on it.

## 3. MMU and banking (H, PRG)

| Address | Register |
|---|---|
| `$d500` / `$ff00` | Configuration register (CR): RAM bank 0/1 for CPU access, ROM/I/O visibility. `$ff00` is always visible |
| `$d501-$d504` / `$ff01-$ff04` | Preconfiguration registers A–D: a write to `$ff0n` loads PCR n into the CR |
| `$d505` | Mode: bit 0 = 8502/Z80, bit 6 = C64 mode, bit 7 = 40/80 key sense |
| `$d506` | RAM configuration: common RAM size and position (top/bottom, 1–16 KB), VIC bank bits |
| `$d507-$d50a` | **Page 0 and page 1 pointers: relocate zero page and stack** |
| `$d50b` | Version |

- **128 KB RAM** in two 64 KB banks. Keep code and the zero page in bank 0 and tile and map data in bank 1, reached with `$ff00` switches or the common-RAM window.
- **Zero-page relocation** (`$d507/$d508`) gives the engine a private ZP: no conflicts with KERNAL ZP use, and cheap context switches.

## 4. C128-mode KERNAL and loading (H, PRG)

**Extra jump table** (C128 mode):
- `$ff47` SPIN_SPOUT (fast serial setup)
- `$ff4a` CLOSE_ALL
- `$ff4d` C64MODE
- `$ff50` DMA_CALL (REU)
- `$ff53` BOOT_CALL
- `$ff56` PHOENIX
- `$ff59` LKUPLA, `$ff5c` LKUPSA
- `$ff5f` SWAPPER (40/80)
- `$ff62` DLCHR (copy the character set to the VDC)
- `$ff65` PFKEY
- **`$ff68` SETBNK** (bank for LOAD data and for the filename)
- `$ff6b` GETCFG
- `$ff6e` JSRFAR, `$ff71` JMPFAR
- `$ff74` INDFET, `$ff77` INDSTA, `$ff7a` INDCMP
- `$ff7d` PRIMM

**LOAD into bank 1:** call `SETBNK` (A = data bank, X = filename bank) before `LOAD`.

**1571 burst / fast serial:**
- In C128 mode, `LOAD` from a 1571 or 1581 automatically uses the fast serial protocol (the CIA shift register on the SP line): several KB/s, against ~0.4 KB/s for the 1541 protocol.
- This works on real 1571/1581s and in VICE with true drive emulation.
- **sd2iec does not implement burst** (L 🔧), so it falls back to the slow protocol.
- The Ultimate II+ emulates a 1541 (and 1571/1581 on newer firmware, M).

**Loading summary:** KERNAL `LOAD` with `SETBNK` stays the portable choice. Lowercase PRG names and wildcard names work as on the C64.

## 5. Sound, timing

- **Sound:** the same SID at `$d400`. Stereo via a second SID as on the C64; VICE allows `-sid2address` for x128, including `$d420`, `$de00` and `$df00`.
- **Timing:** PAL/NTSC as on the C64 (c64.md §1). At 2 MHz the CPU gets ~2× the cycles; the VDC runs on its own 16 MHz dot clock.
- **VDC vertical blank:** the status bit 5 of `$d600`. Use it for flips.

## 6. C64 build on a C128 (C64 mode)

- `$d030` bit 0 = 2 MHz works in C64 mode (VICE ✓: reads `$fc`/`$fd`).
- The VIC-II needs the bus during the display window, so switch to 2 MHz only for the lines **outside** it: ~ lines 251–311 and 0–50 on PAL, ≈ 36% of the frame.
- **Estimate for the stock C64 path:** ~1.3× speed on a 175 ms step (draw time spread over frames, ~⅓ of them at 2×). It needs a raster IRQ pair to toggle `$d030`, plus 1 MHz during REU DMA and KERNAL I/O. M (estimate) 🔧
- Ultimate "TurboEnable Bit" mode uses the same `$d030` bit 0, so the same code path serves both. Don't confuse the two: check `$d031` / UCI first (ultimate.md §2).

## 7. Hardware checklist

- [ ] CPU write/read speed through R31 on a real 8563 and 8568, with and without vertical blank.
- [ ] Block copy/fill speed on real silicon, compared with VICE's 1.47 / 0.85 µs per byte.
- [ ] Attribute cells with R9 = 1 or 3 in bitmap mode on 8563 vs 8568 (both revisions).
- [ ] 64 KB detection on a 16 KB machine.
- [ ] 2 MHz-in-border in C64 mode: no VIC-II glitches with sprites near the viewport bottom.
